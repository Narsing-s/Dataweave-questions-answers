# Final Gaps A450-A451 — DataWeave Component Packaging

These questions cover a current DataWeave 2.12 library-packaging behavior that was not represented as a dedicated scenario in the curated bank. They are intentionally focused on build/package-time component metadata rather than repeating the existing component-descriptor type questions in A356-A357.

## A450 — Maven package generation of `dw-components.dwl`

**Question:** A DataWeave library contains `.dwl` modules under `src/main/dw` and uses `internal` declarations. During a production Maven build, how is the component descriptor created and where is it placed in the generated JAR?

**Difficulty:** Advanced  
**Topic:** DataWeave library packaging / component metadata / Maven build

**Expected behavior:** The DataWeave Maven `data-weave:package` goal scans `src/main/dw`, derives the DataWeave resource names, generates `target/generated-dataweave-metadata/dw-components.dwl`, and packages that descriptor into the JAR at `META-INF/dw-components.dwl`. The component name defaults to the Maven `artifactId`.

**Explanation:** In DataWeave 2.12, component descriptors identify which modules belong to a component so the compiler can enforce `internal` visibility. The descriptor is normally generated by the Maven plugin rather than manually maintained.

**Common mistake:** Assuming `dw-components.dwl` must be hand-written in `src/main/dw`, or assuming the descriptor is only an IDE artifact. It is generated as build metadata and packaged into the library JAR.

**Interview tip:** Explain the relationship: DataWeave module -> component descriptor -> component ownership -> compile-time visibility resolution.

## A451 — Test packaging and `internal` access from `src/test/dw`

**Question:** A DataWeave library has an `internal` helper in `src/main/dw` and a test mapping in `src/test/dw` that imports that helper. What is special about the DataWeave Maven test build that allows this access without exposing the helper as public?

**Difficulty:** Advanced  
**Topic:** DataWeave testing / component packaging / internal visibility

**Expected behavior:** The DataWeave `data-weave:test` build scans both `src/main/dw` and `src/test/dw`, so the test files are associated with the same component as the production sources they exercise. This allows tests to access `internal` directives without making those directives public or adding another visibility exception.

**Explanation:** `internal` is component-scoped. Keeping production helpers `internal` preserves encapsulation while allowing the library's own test mappings to exercise them. This is a build/component relationship, not a runtime access mechanism.

**Common mistake:** Making the helper `public` only so the test can import it, or assuming `src/test/dw` automatically forms an unrelated component that cannot see production internals.

**Interview tip:** Distinguish file-local `private` access from component-level `internal` access, and explain why the Maven test build must associate test sources with the production component.
